Reverse-Engineering
LinkedIn's Voyager API

Naman — 2026-08-31
Abstract — LinkedIn exposes no public profile API. Its web app, however, fetches every public profile from an internal REST endpoint. By watching live DevTools XHR, we recovered that endpoint, its CSRF recipe, and its flat included[] shape, then built a thin, dependency-light curl_cffi client that speaks it without Selenium, Playwright, or any headless browser. The client is deployed live over HTTPS, gated by API_KEY, and verified by a real fetch of satyanadella (Chairman & CEO at Microsoft) on 2026-08-31. The session is single-use — LinkedIn revokes a borrowed browser li_at after one Voyager hit — so we keep csrf-token in lockstep with a rotating JSESSIONID and preserve the first result in a TTL cache. This bible is the append-only record of that arc.

We started where every break starts: a normal browser, a public profile, and DevTools open on Network → XHR. What follows is not a tutorial for bulk harvesting, but a forensic log of how the private API was found, how it authenticates, and how it punishes you — written as a -style append-only bible inside a classic paper skin.

1. Capture — 2026-08-30

Decision · 2026-08-30 — Use the frontend's own endpoint

Login in a clean Firefox dedicated, open linkedin.com/in/satyanadella, filter XHR/Fetch. The app issues:

GET https://www.linkedin.com/voyager/api/identity/dash/profiles
  ?q=memberIdentity
  &memberIdentity={slug}
  &decorationId=com.linkedin.voyager.dash.deco.identity.profile.FullProfileWithEntities-93

Two endpoints matter: dash/profiles (primary profile + experience/education/skills/certs/languages/images/about) and profileContactInfo (email/websites/twitter — gated, often empty). The response is a normalized store: a flat included[] array; the primary profile is the entry whose entityUrn contains fsd_profile: and firstName.

2. Auth recipe — Wall 1: 403 CSRF

Wall · 2026-08-30 — Every naive scraper dies here

Wall 1: Sending only li_at returns 403 CSRF check failed. LinkedIn checks csrf-token == JSESSIONID cookie (quotes stripped).

Recipe (the part docs don't tell you): li_at (login) + JSESSIONID (same session) + csrf-token header equal to JSESSIONID.strip('"') + x-restli-protocol-version: 2.0.0 + accept: application/vnd.linkedin.normalized+json+2.1. If the jar lacks JSESSIONID we synthesize :{19–20 digits} — it is matched, not validated. We send the full linkedin.com jar (24 cookies: lidc, bcookie, dfpfpt…), not a leaked token — that is the fidelity fix. Implemented in linkedin_scraper.py:149 via curl_cffi.Session(impersonate="chrome") for JA3.

3. Response shape

Decision · 2026-08-30 — Flat store dispatch

Primary profile: entityUrn with fsd_profile:. Siblings keyed by $type suffix: …Position, …Education, …Skill, …Certification, …Language. _find_profile + fallback on publicIdentifier == slug handles schema drift. profilePicture.vectorImage → first artifact builds a usable URL; coverPhoto similarly.

4. Walls, briefly

Wall 2 — Decoration pin: FullProfileWithEntities-93 rotates every 4–8 weeks. Fix: re-capture from live traffic; the client surfaces a clear 200 with no included error.
Wall 3 — Fingerprint lie: x-li-track: {osName:"Windows"} while sec-ch-ua-platform:"macOS". Fraud score. Fix: osName → "macOS" to match UA.
Wall 4 — Single-use session: LinkedIn revokes a borrowed browser li_at after one Voyager hit (the first satyanadella succeeded, the next distinct slug 401 and the browser's li_at vanished). Fixes: (i) _sync_csrf() — keep csrf-token in lockstep with a rotating JSESSIONID Set-Cookie, retry once on 403; (ii) preserve the first result in a TTL cache so the demo stays servable after logout; (iii) operational: log in, immediately warm the needed profile, keep volume low.

6. Ethics & The Unfair Cyberworld

This is participant-observation research — we document the exact header recipe LinkedIn's own frontend uses, as captured live. The act violates LinkedIn ToS §8.2 (automated access). Under U.S. precedent (hiQ Labs v. LinkedIn, 9th Cir.) scraping *public* data is lawful, but storing EU personal data implicates GDPR. Therefore: dedicated dedicated, low volume, TTL cache only (no disk persistence), no resale, and full disclosure here. The unfairness is the point — a low-resource actor can only see the same endpoint by mimicking the browser — so we record it plainly, with mitigations, rather than pretending the wall doesn't exist.
